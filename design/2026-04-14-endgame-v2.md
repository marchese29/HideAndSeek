## 1. Proximity Tier Model

### Overview

The server monitors seeker locations relative to the hider's hiding zone using distance rings. A `proximity_tier` on the Game reflects the current threat level. Seekers are never informed.

### Tiers

| Tier | Distance threshold | Meaning |
|------|-------------------|---------|
| `none` | Beyond 4× effective hiding zone radius | No seekers nearby |
| `approaching` | Within 4× radius | Seekers in the area |
| `near` | Within 2× radius | Seekers closing in |
| `entered` | Within 1× radius (inside hiding zone) | Seekers in the zone — hiders must freeze |

The tier multipliers (4×, 2×, 1×) are fixed for now. **Future bead**: configurable at game creation.

For a default medium/metric game (500m hiding zone radius): `approaching` = 2,000m, `near` = 1,000m, `entered` = 500m. Thresholds scale with the effective radius, including expansion from the hider powerup.

### Escalation and de-escalation

Asymmetric rules prevent notification flicker:

- **Escalate** (any single seeker): when a seeker location update places them inside a closer tier than the current `proximity_tier`, the tier escalates immediately.
- **De-escalate** (all seekers unanimous): the tier only drops when every seeker's latest position is at or beyond a farther tier. It drops to the tier of the **closest** remaining seeker (not all the way to `none`).

Example: Seeker A enters the hiding zone — tier escalates to `entered`. Seeker B is at 3× radius (`approaching`). Seeker A leaves to 1.5× radius (`near`). Now the closest seeker is A at `near`. Tier de-escalates to `near` (not `approaching`, because A is still within 2×).

### Computation

Runs on every seeker location update during seeking, after hider station election:

1. Compute the reporting seeker's `ST_Distance` to hider station.
2. Determine that seeker's individual tier from the distance thresholds.
3. If the seeker's tier is closer than the game's `proximity_tier` → **escalate** to that tier.
4. If not escalating, query the latest `LocationUpdate` for every other seeker, compute distances, find the **closest** seeker's tier across all seekers. If that tier is farther than `proximity_tier` → **de-escalate** to it.

Step 4 only runs on non-escalation updates — the common case (seekers far away, no change) skips it entirely.

### Data model

`Game` gains:

- `proximity_tier` — `ProximityTier` enum, default `none`.

```python
class ProximityTier(StrEnum):
    none = 'none'
    approaching = 'approaching'
    near = 'near'
    entered = 'entered'
```

No per-seeker proximity state is stored. Individual distances are computed from latest `LocationUpdate` rows on the fly.

### Events

Two new gameplay events, **hider channel only**:

```python
class ProximityEscalatedEvent(GameplayEventSchema):
    """Seekers moved closer — hider channel only."""
    tier: ProximityTier

class ProximityDeescalatedEvent(GameplayEventSchema):
    """All seekers pulled back — hider channel only."""
    tier: ProximityTier
```

New `GameplayEventType` values: `proximity_escalated`, `proximity_deescalated`.

New `PushEventType` values: `proximity_escalated`, `proximity_deescalated`.

### Push messages

| Transition | Push text |
|------------|----------|
| Escalate → `approaching` | "Seekers are in your area" |
| Escalate → `near` | "Seekers are getting close" |
| Escalate → `entered` | "Seekers are in your hiding zone — stay put!" |
| De-escalate → `near` | "Seekers left your zone — you may reposition" |
| De-escalate → `approaching` | "Seekers have pulled back" |
| De-escalate → `none` | "Seekers are no longer nearby" |

### State delivery

`HiderGameStateResponse` gains `proximity_tier: ProximityTier` for SSE snapshot hydration on reconnect.

### Seeker visibility

Seekers receive **no** proximity events, push notifications, or visual changes. The system is entirely hider-facing.

## 2. Hider Freeze Mechanic

When `proximity_tier == entered`, hiders must stay put. Enforcement is via nag (warning, not hard blocking — the game relies on sportsmanship).

### Freeze position

`Player` gains:

- `freeze_location` — `ShapelyGeography('POINT')`, nullable.

Set to each hider's latest reported position when the tier escalates to `entered`. Nulled out when the tier de-escalates from `entered`. All hiders' freeze positions are set/cleared together (game-level tier), but each hider's captured position is individual.

### Departure detection (edge-triggered)

Freeze departure follows the same pattern as hiding zone departure (`not_in_zone`): a field on the hider location event that mobile uses for reactive UI, with push notifications fired only on **state transitions**.

On every hider location update while `proximity_tier == entered`:

1. Compute geodesic distance from the hider's new position to their `freeze_location`.
2. If the distance exceeds **50 meters** (above GPS jitter of 10–20m), the hider is "freeze-departed."

The `PlayerLocationEvent` gains an optional `freeze_departed` field (list of hider player IDs who are freeze-departed, same shape as `not_in_zone`). Computed fresh on each hider location update during `entered` tier. `null` when not in `entered` tier.

**Push notification** fires only on the transition from not-departed to departed — the server compares the new `freeze_departed` set to the previous state. The nag targets **all hiders**: "A hider moved during freeze — stay in your spots!" This matches the existing all-hiders departure warning pattern.

**Note**: The existing `not_in_zone` departure warnings are banner-only today (no push). Adding push with the same edge-triggered pattern is a small follow-up.

`HiderGameStateResponse` gains `freeze_departed: list[uuid.UUID] | null` for reconnection hydration.

### Hiding zone color (mobile)

When `proximity_tier == entered`, the hider's hiding zone overlay changes from blue (`#3498DB`) to amber (`#F59E0B`). Reverts on de-escalation from `entered`.

### Freeze departure banner (mobile)

A `FreezeWarningBanner` (similar to `DepartureWarningBanner`) renders when `freeze_departed` is non-empty. Red background, resolves player IDs to names: "[Name] moved during freeze!" Auto-dismisses when all hiders return to their freeze positions.

Seeker rendering is unaffected by freeze state.

## 3. More Modal

### Current state

The utility belt right section has two buttons: info (placeholder) and leave (exit-run icon). The leave button triggers nested `Alert.alert()` chains for leave/kick/end flows.

### New design

Replace both buttons with a single **"more" button** (ellipsis icon). Tap opens a **bottom sheet modal** (`presentationStyle: "pageSheet"`, swipe-to-dismiss) with a standard preferences-style list layout.

### Modal options

| Option | Who sees it | Condition |
|--------|------------|-----------|
| Stats | Everyone | Always (placeholder for now) |
| Preferences | Everyone | Always (placeholder for now) |
| Leave Game | Everyone | Always |
| End Game | Host only | Game is active |
| Kick Player | Host only | Other players exist |

Tapping an option does a **screen replacement within the modal** — no nested alerts:

- **Stats** → placeholder screen ("Coming soon")
- **Preferences** → placeholder screen ("Coming soon")
- **Leave Game** → confirmation screen → host transfer picker if needed → `DELETE /players/{id}` → dismiss, navigate home
- **End Game** → confirmation screen ("This will end the game for everyone") → `POST /end` → dismiss
- **Kick Player** → player picker → confirmation → `DELETE /players/{id}` → dismiss

Swipeable-to-dismiss at any point. Each sub-screen has a back button.

## 4. Seeker Endgame View

The endgame view is a **phone-local seeker state** — not a server-side mode. Each seeker independently chooses when to enter endgame view, which station to investigate, and which question marks the cutoff. Multiple seekers can simultaneously research different endgame scenarios. The game rules do not change — questions are still askable and all normal seeker functionality works.

### Belt utility function

Endgame is the **first utility belt function for seekers**. When the belt center is in its default state (no question selection active), it shows utility buttons in a single row with a flat table style: large icon above, text label below, both black, thin gridlines separating items, fully transparent backgrounds (no button chrome). For now the only utility is "Endgame."

| Belt center state | Content |
|-------------------|---------|
| Default (no selection) | Utility button row (just "Endgame" for now) |
| Question selection active | Type bar / param picker / custom input (unchanged) |
| Endgame view active | "Found" + "Back" buttons (same flat table style) |

The state action button ("Questions" / "Browse") works normally during endgame view — tapping it opens question selection, temporarily replacing Found/Back with the type bar. Closing question selection returns to Found/Back.

### Initialization flow

1. Seeker taps "Endgame" in the belt center utility row.
2. **Station picker**: candidate stations (stops not fully excluded by the long-game `total_exclusion`) become tappable on the map. Uses the existing `GET /candidate-stations` endpoint (seeker-only, checks `NOT ST_Covers(total_exclusion, hiding_zone_circle)`). Renders dots similar to `CandidateStopOverlay` — blue dots, green when highlighted. Non-candidate stops remain inert. Dismissal from station selection is handled at the bead planning level.
3. Seeker taps a candidate station → station highlights green, station name shows in the belt center.
4. **Question cutoff modal**: a bottom sheet presents answered questions in chronological order. Each row shows: question type icon (colored per `questionColors.ts`), category or distance label. The seeker taps the question **after which** the endgame view begins.
5. Mobile calls `GET /endgame-exclusions?station_id={stop_id}&after_question={sequence}`.
6. Endgame view activates.

### Endgame view rendering

Map centers on the hiding zone (same camera animation pattern as hider station election) and shows:

- **Hiding zone border** — blue stroke only (`#3498DB`, no fill). Outline marks the boundary of the zone without obscuring the inclusion/exclusion areas inside it.
- **Inclusion zone** — server-computed area within the hiding zone that is **not** excluded. Rendered as a blue fill (`rgba(52, 152, 219, 0.15)`). This is where the hider could be. Comes directly from the `safe_zone` field on the endgame exclusions response (see server changes below).
- **Endgame exclusion** — the `total_exclusion` from the endgame exclusions response (clipped to the hiding zone by the server). Rendered in the standard red (`rgba(231, 76, 60, 0.25)`).
- **Long-game total exclusion hidden** — the full-map red exclusion overlay is suppressed while endgame view is active. Long-game exclusions are unreliable during endgame because hiders were free to move within their zone during the long game.

As more questions are answered, the inclusion zone shrinks and the exclusion grows — the seeker can visually narrow down where the hider must be.

### Server changes: `safe_zone` field

The `GET /endgame-exclusions` response gains a top-level `safe_zone` field:

```python
class EndgameExclusionsResponse(BaseModel):
    hiding_zone: GeoJSONGeometry       # existing — circle clipped to boundary
    safe_zone: GeoJSONGeometry | None  # NEW — hiding_zone minus total_exclusion
    entries: list[EndgameExclusionEntryResponse]
```

`safe_zone` is computed server-side as `hiding_zone.difference(total_exclusion)` where `total_exclusion` is the cumulative exclusion from the last entry. `None` if no entries have exclusions (the entire zone is safe). This avoids geo math on mobile.

### Live updates during endgame

When a new question is answered while in endgame view:

1. The `question_answered` SSE event fires as normal (updates long-game `total_exclusion` in the store — kept for when the seeker exits endgame view).
2. Mobile re-fetches `GET /endgame-exclusions` with the same `station_id` and `after_question` to get the updated endgame exclusions including the new answer.
3. The endgame overlays re-render with the fresh geometry.

This re-fetch is necessary because the endgame exclusion is server-computed and phone-local — each seeker's station + cutoff may differ.

### Mobile state

Endgame view state lives in the gameplay Zustand store (seeker side):

```typescript
endgameView: {
  stationId: string;
  afterQuestion: number;
  hidingZone: GeoJSON;            // hiding zone circle (outline only)
  safeZone: GeoJSON | null;       // inclusion area (blue fill)
  totalExclusion: GeoJSON | null; // endgame exclusion (red fill)
} | null;
```

When `endgameView` is non-null:
- Hiding zone renders as outline only (no fill).
- Safe zone renders as blue fill inside the hiding zone.
- Endgame exclusion renders as red fill inside the hiding zone.
- Long-game total exclusion overlay is hidden.
- Belt center shows Found/Back.

When null (exited via "Back"): normal long-game rendering resumes.

## 5. Two-Party Game Completion

The game ends when seekers physically find the hiders. Both sides must agree.

### Flow

```
Seeker taps "Found" in endgame belt
  → POST /found
  → Server validates: seeking phase, seeker role, location within hiding zone, no pending claim
  → Server records pending claim, schedules 2-minute auto-dismiss timer
  → FoundClaimEvent to hider channel (SSE + push)

Hider sees auto-presented modal
  → Confirm: POST /found/confirm → game finishes (reason: found)
  → Reject:  POST /found/reject  → claim dismissed, seekers notified
  → Ignore:  timer fires → claim auto-dismissed, both sides notified
```

### Seeker-side validation

`POST /games/{game_id}/found` validates:

- Game is in `seeking` status.
- Player is a seeker.
- Seeker's latest location is within the hiding zone (`ST_Distance` to hider station ≤ `effective_hiding_zone_radius_m`). Prevents remote claims.
- No other claim is pending (`found_claim_at IS NULL`). 409 if one exists.

### Hider-side modal

On `FoundClaimEvent`, mobile auto-presents a modal:

- "A seeker says they found you!"
- **Confirm** button → `POST /found/confirm`
- **Reject** button → `POST /found/reject`
- Swipe-to-dismiss **disabled** (forces a decision or timeout).

Any single hider can confirm or reject — first response wins. If two hiders confirm simultaneously, the first transitions the game; the second gets 409 (game already finished) and mobile navigates to the recap screen.

### Auto-dismiss timer

Celery task with ID `found_claim:{game_id}`. Fires after 2 minutes. If `found_claim_at` still matches, clears the claim and emits `FoundClaimExpiredEvent` to both channels.

### Data model

`Game` gains:

- `found_claim_at` — `DateTime`, nullable.
- `found_claim_player_id` — UUID FK → Player, nullable.
- `end_reason` — `EndReason` enum, nullable. Set on finish or dissolution.

```python
class EndReason(StrEnum):
    found = 'found'
    host_ended = 'host_ended'
    dissolved = 'dissolved'
```

### Endpoints

| Method | Path | Who | Description |
|--------|------|-----|-------------|
| `POST` | `/games/{id}/found` | Seeker | Claim found. Validates proximity. 204. |
| `POST` | `/games/{id}/found/confirm` | Any hider | Confirm claim. Game → finished. 204. |
| `POST` | `/games/{id}/found/reject` | Any hider | Reject claim. Clears state. 204. |

### Events

```python
class FoundClaimEvent(GameplayEventSchema):
    """A seeker claims to have found the hiders — hider channel only."""
    seeker_player_id: uuid.UUID

class FoundClaimRejectedEvent(GameplayEventSchema):
    """Hiders rejected the found claim — seeker channel only."""

class FoundClaimExpiredEvent(GameplayEventSchema):
    """Found claim timed out — both channels."""
```

New `GameplayEventType` values: `found_claim`, `found_claim_rejected`, `found_claim_expired`.

## 6. Host End Game Rework

`POST /games/{game_id}/end` gains `end_reason` tracking:

- Host ends game → `end_reason: 'host_ended'`
- Two-party found → `end_reason: 'found'`
- Dissolution → `end_reason: 'dissolved'`

`GameEndedEvent` gains a `reason` field:

```python
class GameEndedEvent(GameplayEventSchema):
    """Game ended for all players — both channels."""
    reason: EndReason
```

`GameDissolvedEvent` keeps its existing `reason: str` for specifics (`'last_player'`, `'no_hiders_remaining'`, etc.). `EndReason.dissolved` is the high-level category.

## 7. Recap Screen

When a game ends, mobile navigates to a recap screen instead of showing `Alert.alert()` and redirecting home.

### Content

- **Header**: "Game Over"
- **Reason line** (role-aware):

| End reason | Hider sees | Seeker sees |
|------------|------------|-------------|
| `found` | "The seekers found you!" | "You found the hiders!" |
| `host_ended` | "The host ended the game" | "The host ended the game" |
| `dissolved` (no hiders) | "No hiders remaining" | "No hiders remaining" |
| `dissolved` (no seekers) | "No seekers remaining" | "No seekers remaining" |
| `dissolved` (last player) | "All players left" | "All players left" |

- **Home button**: clears game state, navigates to `/`. No back button.

### Navigation

Replaces the current `Alert.alert()` + `clearSession()` + `router.replace('/')` pattern:

1. On `game_ended` / `game_dissolved` SSE event → navigate to recap screen (reason + role as route params).
2. On mount → close SSE connection, clear gameplay store.
3. On "Home" tap → clear session credentials, navigate to `/`.

## Notification Delivery

All endgame notifications use the same dual-channel pattern unless otherwise stated:

- **SSE event** to the appropriate gameplay channel (hider, seeker, or both).
- **Push notification** via APNs/FCM for background delivery.
- **Foreground**: toast (existing `expo-notifications` banner handler) + haptic buzz.

Applies to: proximity tier changes, freeze departure nags, found claims/rejections/expirations.

## API Hardening

`GET /games/{game_id}/hiding-zone` currently uses `get_player_in_game` (no role gate). A seeker could call it directly if they guessed a station ID. Fix: change to `get_hider_in_game`. Seekers get the hiding zone geometry through the `GET /endgame-exclusions` response (already seeker-only gated).

## Resolved Beads

**HideAndSeek-vg2** (question slicing on candidate stations): the primary use case — seekers analyzing exclusions from a question cutoff onward — is fully addressed by the seeker endgame view. The seeker picks a station and an `after_question` cutoff, and `GET /endgame-exclusions` computes the sliced exclusions. `GET /candidate-stations` does not need `after_question` — it uses the full question set to determine which stations are still viable, which is the correct filter for the station picker. Close vg2 in favor of this design.

## What Does NOT Change

- **Question lifecycle** — ask, answer, exclusion computation, inventory depletion. Questions work identically during endgame view.
- **Geo math** — all server-side, meters.
- **Location tracking** — 10-second polling for all players.
- **Hider visibility rules** — seekers never see hider locations.
- **GameStatus enum** — no new values. `seeking` covers the entire post-hiding phase.
- **Endgame exclusion endpoint** — `GET /endgame-exclusions` works as-is (seeker-only, clips to hiding zone, supports `after_question`). Gains one new response field (`safe_zone`).
- **Question inventory** — no reset for endgame. Remaining slots carry over. Tentacles are designed for dense endgame areas but are askable at any point.
